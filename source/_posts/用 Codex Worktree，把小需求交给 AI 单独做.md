之前聊过怎么通过 AGENTS.md、Skills 和工具，让 Codex 更好地理解项目、完成需求。这篇再聊一个很适合搭配 AI 编程使用的 Git 功能：**worktree**。

它不是什么新东西，但放到现在的 vibe coding 场景里，确实有了一个很顺手的用法。

比如，你手上正在做一个需求，代码改了一半。这时候又来了一个小调整：列表页加个筛选重置按钮，或者修一下弹窗关闭后状态没有清空的问题。

需求不大，描述清楚后，完全可以先交给 Codex 做。但如果它直接在你当前目录里改，两个需求的代码就容易混到一起。

**worktree 的价值就在这里：给这个小需求单独安排一个工作目录，让 AI 先做，你继续手头的事情，做完再回来验收。**

## 已经有分支了，为什么还需要 worktree？

平时开发，我们通常是一个项目目录，切换不同分支。

分支能区分不同需求的提交，但在同一个目录里切分支，目录中的文件也会随之变化。当前有未提交改动时，还要考虑先提交、stash，或者处理切换被阻止的情况。

如果这个目录里还有一个 AI 任务正在读文件、改代码，你再切一次分支，它接下来看到的内容可能就变了。

worktree 可以让同一个 Git 仓库拥有多个工作目录，每个目录保留自己的文件、暂存区和 HEAD，也就是当前检出的提交位置。

例如：

```text
workspace/
├── my-app/                 # 你正在做的主需求
├── my-app-filter-reset/    # Codex：增加筛选重置
└── my-app-dialog-fix/      # Codex：修复弹窗状态
```

三个目录可以同时存在，各自修改各自的文件，共享仓库的提交历史和分支信息。

它比重新 clone 几份仓库更省事，也不需要在同一个目录里反复切换任务。

不过要注意，**多开几个 Codex 对话，并不等于隔离了代码。** 如果这些对话都在同一个 Local 目录里执行，它们依然可能同时修改同一批文件。真正提供文件隔离的是各自独立的 worktree。

## 为什么我觉得它很适合小功能？

AI 写代码之后，很多小需求的节奏变了。

以前要自己找入口、写逻辑、补样式。现在把需求、约束和验收标准说清楚，Codex 就能先完成一版，我们再检查结果。

这时适合交出去的任务，通常有几个特点：改动范围明确、能独立验证、和手头需求没有太多依赖。

比如：

- 列表页增加筛选重置。
- 修复弹窗重复打开时的数据残留。
- 调整一个页面的移动端布局。
- 给已有请求补上按钮 loading，避免重复提交。

这类任务和 worktree 很搭。你不用为了一个小调整中断主线工作，也不用把 AI 的试验代码直接混进当前改动里。

当然，不能只看“改了几行”。一个公共请求方法可能只改五行，却影响整个项目；一个独立页面改了上百行，反而更容易单独验收。

**比代码量更重要的是，任务的边界能不能说清楚。**

## 在 Codex 里，怎么开始一个 Worktree 任务？

其实直接和 Codex 对话就行。

比如，要给订单列表加一个筛选重置按钮，可以这样说：

> 我要给订单列表增加一个筛选重置按钮，点击后恢复初始筛选条件，回到第一页并重新请求列表。
>
> 帮我基于最新的 main 分支，新建一个 worktree 工作目录，创建一个新的功能分支，在这个目录里完成改动。
>
> 改完运行项目已有的相关检查，再启动预览服务，给我一个可以直接访问的预览地址。

接下来就可以继续做自己的事情，等它把结果交过来。

拿到地址后，打开页面看看效果，再检查一下代码改动。有问题就继续在这次对话里提，让它调整到符合预期。

预览没问题了，再告诉它：

> 预览没问题了，帮我按项目规范提交代码，把这个功能分支合并到 test 分支并推送。
>
> 然后创建一个从这个功能分支合并到 main 的 MR，把 MR 地址发给我，主干合并留给后续审核。

这样，从开发、预览到提交测试、发起主干合并请求，整个流程就串起来了。

这里以“功能分支合入 test 验证，再由功能分支向主干发 MR”的流程为例，避免把 test 里其他尚未上线的需求一起带到主干。团队有自己的发布流程，就让 Codex 按团队规则执行。GitHub 中对应的合并请求叫 PR。

当然，推送和创建 MR 的前提，是本机已经配置好对应代码平台的工具和登录权限；如果 test 是保护分支，也要走平台要求的合并请求流程。

## 常用约束，写进 Skill 就好

每次都要交代分支怎么命名、commit 怎么写，确实有点啰嗦。这些固定规则可以整理进项目的 Skill，再在 AGENTS.md 里约定做这类任务时读取。

例如：

- **分支命名**：统一使用 `qzai/` 前缀，后面跟简短的功能描述，例如 `qzai/order-filter-reset`。
- **提交规范**：新功能用 `feat:`，修复用 `fix:`，提交说明写清楚这次具体做了什么。
- **改动范围**：只提交当前需求相关文件，不顺手重构其他模块，也不混入原目录里未完成的改动。
- **预览要求**：在对应 worktree 中启动服务，使用空闲端口，完成后返回完整的页面地址。
- **交付流程**：先预览验收，确认后再合入 test、创建主干 MR。

把这些习惯固定下来，以后就主要描述“这次要做什么”，不用每次都重新交代一遍开发流程。

## 用 worktree 时，留意这几个问题

worktree 用起来方便，但多个目录毕竟共用一个 Git 仓库，有些地方还是要留意：

- **同一个分支，默认不能在两个目录里同时检出。** 比如功能分支已经在 worktree 中使用，你再去原项目里切到它，Git 就会提示分支被占用。可以直接去对应目录操作，或者使用 Codex 的 Hand off 移交。
- 目标分支如果在另一个 worktree 中使用，切换过去会受阻；当前目录有未提交改动、分支发生分叉等，也仍然可能导致 pull 失败或需要处理冲突。先让 Codex 确认所在目录和分支，别用强制操作绕过去。
- **分支信息是共享的，文件不会跟着一起更新。** 一个目录执行 fetch 后，其他目录也能看到更新后的远程跟踪分支；但各目录检出的代码仍要分别更新。删除分支等操作也会影响整个仓库，不能把每个 worktree 当成完全独立的 clone。
- **依赖和本地配置可能需要重新准备。** 新目录不能默认就有 `node_modules`、`.env.local` 这些被 Git 忽略的内容，可以让 Codex 在启动预览前按项目要求处理好。
- **预览端口不能撞车。** 原项目占用了 `3000`，新 worktree 就换一个空闲端口。同时跑几份项目时，要确认打开的是当前任务的地址；如果连接同一套后端，测试数据仍然会相互影响。
- **开发互不打扰，合并仍可能冲突。** 两个任务改到同一块逻辑，最终合并时还是需要处理，处理完也要重新验证。
- **用完记得清理。** 多个 worktree 的依赖和缓存会占磁盘。代码确认保留后，可以让 Codex 停掉预览服务、移除不再需要的 worktree，再按团队规则清理分支；还在等待 MR 审核的分支先留着。

## 未来展望

看到网上很多人有不少巧思，例如把任务文档连接到 Codex。只要把任务描述写好，点击运行，AI 就直接开干了。

其实拆解下来，这类流程就可以用 worktree 来实现：读取任务文档，创建独立的工作目录和功能分支，完成开发和验证，再做代码 Review、发起 MR。审核通过后合入主干，由项目的发布流程完成上线。

我们前面通过几轮对话完成的事情，就这样被串成了一条自动化流程。任务文档负责讲清楚做什么，Skill 约定怎么做，worktree 给每个任务提供独立的开发空间。
